# LAN Paced: negative functional findings — November 1, 2026

The LAN trace did not support a fresh-clock or token-bypass patch. Within the retained eight-second windows of 12 RSH sessions, no pending-output gate was blocked by tokens. All 1,418 catch-only gates used the ordinary 10 ms budget, and none expired between the stored logical-now and the later trace-row timestamp. No 300 ms catch-only gates were observed. These are bounded negative observations, not proof that fresh-clock changes can never help.

The cohort contains 16 functional-valid jobs, 24 trace endpoints and 7,679 complete bodies, using four workers and two evaluations per scene. Performance eligibility is false. The host-context rejection for `02-lan-bandwidth-i0` remains recorded. Both baseline A/A roles reuse the traced CAN+PTY baseline (d742, production 4f98); the combined role is traced controller295f (3031). It is not a test of later quarter/margin policies.

The startup-only hypothesis was also unsupported for most worst gaps. A predeclared descriptive split at 0.5 seconds placed 57 of the 60 worst RSH adjacent body gaps wholly later, one wholly earlier and two across the boundary. Refill medians during the retained window were 14.784–14.922 ms. This does not deny the initial 30 ms setting at process creation: adaptation can occur before the official window. Official low calculations retain the entire window.

Gate event 7 records state after refill and before token consumption; event 8 is after consumption. Dashboard pending gates were ready 2,877 times; random pending gates were ready 2,882 times and catch-only 1,418 times. Token-only and token-plus-catch counts were zero. Under the stored milli-token interval and the specified next-poll/no-intervening-write conditions, robust and possible row-time fresh-refill candidates were both zero. The separate catch check likewise found zero deadline crossings.

The row timestamp is a later observed point in the flush sequence; using it for a hypothetical fresh call is only an upper-time counterfactual. Integer inequalities use the recorded token quantization and a linear refill model; they do not prove every Rust floating-point boundary. Client poll events omit the return code and some FD readiness, so they cannot prove a strict timeout-only delay. Write/gap co-occurrence cannot assign complete producer-frame ownership or GPU presentation. The 300 ms catch path was not exercised by catch-only observations. Random writes sometimes lasted several milliseconds, but this alone identifies no cause.

These findings favor leaving the client policy unchanged pending new evidence. They do not justify removing the minimum poll wait, which can spin on expired deadlines. Earlier sub-millisecond polling results remain mixed and had no branch-activation proof. FPS and lows remain the primary outcomes; this functional appendix does not select a performance winner.
