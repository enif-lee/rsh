# Client positive-submillisecond wait — source draft READY for review

Prepared from exact main+CAN `diff-cancel-source` (tested source93533574fffa). It is **unbuilt and untested**. Product/focused CAN PR, frozen CAN source and all old experiments are unchanged. New tree `client-subms-wait-source` changes only the existing client hot-poll block; the three CAN fixtures remain exact. The31-file canonical inventory and90-file full inventory are separately hashed; the reverse replacement reconstructs all90 parent files.

On Linux only, `0 < wait < 1ms` uses existing libc::ppoll with the same FD pointer/count, a positive nanosecond timespec and null signal mask. Zero/overdue and >=1ms use the exact old poll expression, and non-Linux retains the old poll call. All FD/deadline eligibility, signal/EINTR post-processing, server/wire helpers, controller, dependencies and configuration remain unchanged. This is not LAN-only or TCP-only: any Linux client loop with a positive sub-ms remainder may use the branch.

Hypothesis: avoid rounding a future100µs remainder to1ms. It cannot help an already-due zero remainder, ready data, stalled source/server or scheduling delay. Keeping >=1ms unchanged avoids also lengthening e.g. the old1.75ms→1ms truncation to1.75ms. Keeping overdue1ms avoids a new spin. Actual wake precision, branch frequency and FPS benefit are unmeasured; kernel timer granularity/slack/scheduling still apply. More wakeups or altered batching could cost CPU, age or slow/moving performance despite source-unchanged eligibility.

No new fields, options, dependencies, abstraction or busy-loop mechanism were added. `client-subms-wait.patch`, source/full manifests and `client-subms-wait-proof.json` retain exact preparation hashes. The source-only design memo is in research notes `client-wait-fidelity-source-design.md/json` with official poll/ppoll references.
