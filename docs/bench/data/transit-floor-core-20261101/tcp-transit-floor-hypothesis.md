# Sampled-floor gate for existing TCP transit allowance

Isolated source-only prototype, not built, tested, installed or performance-approved. Parent is `tcp-transit-source`; it keeps main's original0.8 probe threshold. No broad/near0.6 policy, tracing, new state, API or option is combined.

The only production change is the three-line early return in `Sender::drain_bdp`: allowance is absent unless the current sampled `floor_rtt` is at least20ms. `server.rs` production bytes are identical to the existing transit prototype: TCP still calls `drain_bdp`, UDP/modelled still calls `slow_bdp`. At None/<20, the helper returnsNone, `drain_backlog` returns its input, and TCP `stepped_lag==lag`; proactive and stepped screen predicates then have main's values for the same state. This does not roll back state chosen earlier or prove entire executions/tails identical.

Four new unit fixtures are prepared, not executed: reject None/0/19.999 even when a synthetic modelled rate exists; include exact20 and300 with known capacity; deny far floor without any rate/delivery history; and actual Sender send/on_ack near1/19ms leaves both backlog argument shapes unchanged, with unmodelled UDP still unchanged. Two existing far server fixtures now learn their300ms sampled floor through public Sender send/on_ack before installing their synthetic rate. The old set_path-only/floorNone case explicitly denies credit. Existing modelled UDP fixtures are unchanged; production UDP dispatch is byte-identical.

The floor includes application ACK work/scheduling, not physical RTT. Startup LAN CPU/observer delay can still make it>=20; a true WAN with no sampled far floor temporarily gets main behavior. Already-far fast→slow paths can retain recent fast history, and existing reset/idle MIN_WINDOW/2 fallback semantics remain. This gate does not validate continuous demand, fresh physical capacity or empty queues and does not modify input/ACK metadata. LAN tail recovery and WAN/low-bandwidth benefit retention remain unproven.
